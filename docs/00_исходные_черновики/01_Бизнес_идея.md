# Бизнес-идея (запрос Заказчика) — черновик

**Проект:** «Проверка сложности пароля»
**Роль автора:** Заказчик
**Версия:** 0.1 (черновик) · **Дата:** ____

> ⚑ — решение Заказчика не утверждено, обсудить на этапе 1.

## 1. Контекст

Заказчик — служба информационной безопасности (ИБ) условной компании. ⚑ Альтернатива: продуктовая команда онлайн-сервиса, которой нужен виджет для формы регистрации.

## 2. Проблема

Пользователи придумывают слабые пароли: короткие, из одного типа символов, из списков популярных паролей («123456», «password»). Такие пароли подбираются перебором или по словарю, это ведёт к взлому учётных записей.
Пользователь сам не может оценить, насколько надёжен его пароль, и не знает, что изменить.

## 3. Что хочет Заказчик

1. Инструмент, в который пользователь вводит пароль и получает **оценку надёжности** и **конкретные рекомендации**, что исправить.
2. Возможность встроить ту же проверку в другие системы компании (формы регистрации) через **программный интерфейс (API)**.
3. Гарантию, что введённый пароль **нигде не сохраняется**.

## 4. Цели

| ID | Цель | Как поймём, что достигнута |
|---|---|---|
| Ц-1 | Пользователь узнаёт уровень надёжности пароля | На эталонном наборе паролей уровень совпадает с ожидаемым в 100 % случаев (UAT) |
| Ц-2 | Пользователь знает, как усилить пароль | Для каждого невыполненного критерия выводится рекомендация (UAT) |
| Ц-3 | Проверку можно встроить в другие системы | API отвечает по контракту из СТ (интеграционные тесты) |
| Ц-4 | Пароль не утекает | Пароль не найден в логах, ответах и файлах после прогона тестов |

## 5. Стейкхолдеры

| Стейкхолдер | Интерес |
|---|---|
| Служба ИБ (Заказчик) | Меньше слабых паролей |
| Пользователь | Быстро понять, годится ли пароль, и что изменить |
| Разработчики внешних систем | Встроить проверку через API |
| Команда разработки | Однозначные требования, которые можно проверить |

## 6. Границы

**Входит:** веб-форма проверки; API проверки; оценка по фиксированным правилам; рекомендации; встроенный список распространённых паролей.

**Не входит:** хранение паролей и истории проверок; регистрация и авторизация; проверка по внешним базам утечек (например, Have I Been Pwned); генерация паролей ⚑; мультиязычность интерфейса; ограничение частоты запросов (rate limiting).

## 7. Допущения и ограничения

- Учебный стенд, локальный запуск, один пользователь одновременно.
- Стек задан: Python 3.1x, FastAPI, Uvicorn, Jinja2, HTML5, CSS, JS — при необходимости.
- База данных не используется.
- Критерии оценки — фиксированные (захардкожены в конфигурации приложения), их утверждает Заказчик.
