# Чек-листы контроля качества (QC)

## 1. БТ: чек-лист BABOK v3 (6 характеристик)

«Утверждённое» исключено по условию задания.

| # | Характеристика | Вопрос проверки | Признаки нарушения | ✗ → ✓ (наш домен) |
|---|---|---|---|---|
| 1 | Чёткое и лаконичное | Одно ли значение у формулировки? Нет ли лишнего? | слова без метрики (список ниже), «и/или», два требования в одном, местоимения без ясного объекта | ✗ «Система удобно показывает результат» → ✓ «Система показывает балл 0–100, уровень и список рекомендаций на одной странице» |
| 2 | Корректное | Верно ли отражает потребность Заказчика и предметную область? | расходится с бизнес-идеей; неверный факт о безопасности | ✗ «Пароль хранится в зашифрованном виде» (Заказчик просил не хранить вообще) → ✓ «Система не сохраняет введённый пароль» |
| 3 | Полное | Хватит ли информации, чтобы понять и проверить? | нет граничных значений, нет поведения при ошибке, «и т. д.» | ✗ «Система проверяет длину пароля» → ✓ «…минимальная длина 8, максимальная 128 символов» |
| 4 | Непротиворечивое | Не конфликтует ли с другими требованиями и само с собой? | разные пороги в разных местах; разные названия одного объекта | ✗ БТ-01 «4 уровня», а в UI-макете 3 уровня |
| 5 | Проверяемое | Есть ли метрика или критерий, по которому стороны согласятся «выполнено / не выполнено»? | нет числа, нет эталона, «быстро» | ✗ «Результат появляется быстро» → ✓ «…не позднее 1 с после нажатия кнопки» |
| 6 | Трассируемое | Указан ли источник: кто запросил и зачем? Есть ли связь с целью? | нет колонки «Источник», нет ссылки на цель Ц-x | ✗ «Нужен API» → ✓ «…источник: разработчики внешних систем, цель Ц-3» |

**Слова-маркеры нарушения «чёткости»:** удобно, быстро, оптимально, интуитивно, понятно, простой, современный, надёжный (вне названий уровней), достаточно, эффективно, гибко, по возможности, при необходимости, как правило, и т. д., и/или, user-friendly, максимально, минимально (без числа).

### Формат отчёта QC по БТ

| ID | Ч | К | П | Н | Пр | Т | Замечание | Исправленная формулировка |
|---|---|---|---|---|---|---|---|---|
| БТ-01 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | — | — |
| БТ-0x | ✗ | ✓ | ✗ | ✓ | ✗ | ✓ | что не так и почему это проблема | готовый текст |

Ч — чёткое, К — корректное, П — полное, Н — непротиворечивое, Пр — проверяемое, Т — трассируемое.
Итог отчёта: сколько требований проверено, сколько с замечаниями, по каким характеристикам больше всего нарушений.

## 2. СТ: чек-лист

Задание требует проверить полноту, непротиворечивость, тестируемость. Дополнительно проверяем однозначность, атомарность, трассируемость, осуществимость.

### 2.1 Полнота
- [ ] Каждое БТ раскрыто хотя бы одним US/UC и ФТ/НФТ (матрица без пустых строк).
- [ ] Для каждого поля: тип, обязательность, ограничения, поведение на границах.
- [ ] Для каждой ошибки: код, HTTP-статус, текст, где показывается.
- [ ] Алгоритм описан пошагово, порядок шагов однозначен (что раньше: чёрный список или штрафы?).
- [ ] Есть контракт API: запрос, ответ, пример, ошибки.
- [ ] Описан UI: элементы, состояния (пусто, ошибка, результат).
- [ ] НФТ покрывают: безопасность, производительность, удобство, совместимость, сопровождаемость, ограничения.
- [ ] Есть эталонный набор с ожидаемыми результатами.

### 2.2 Непротиворечивость
- [ ] Пороги, длины, баллы совпадают в БТ, СТ, UI, эталонном наборе.
- [ ] Один термин — одно название (глоссарий).
- [ ] Коды ошибок и тексты одинаковы в API и UI.
- [ ] Сумма баллов критериев = 100, уровни покрывают 0–100 без дыр и пересечений.

### 2.3 Тестируемость
- [ ] У каждого ФТ и НФТ есть критерий проверки и способ (авто / ручной / замер).
- [ ] Ожидаемый результат можно вычислить заранее, без «на усмотрение разработчика».
- [ ] НФТ содержат число, условия замера и объём выборки.

### 2.4 Прочее
- [ ] Однозначность: два разработчика реализуют одинаково (см. стресс-тест).
- [ ] Атомарность: одно требование — одна проверка.
- [ ] Трассируемость: у каждого ФТ/НФТ есть источник.
- [ ] Осуществимость: реализуемо в заданном стеке и сроке.

### Формат отчёта QC по СТ

| № | Где (ID / раздел) | Характеристика | Проблема | Чем грозит | Исправление | Критичность |
|---|---|---|---|---|---|---|

Критичность: **блокер** (без исправления нельзя кодить) / **major** (будет баг) / **minor** (оформление).

## 3. Стресс-тест СТ: банк промтов

Используй по очереди, каждый — отдельным запросом.

1. «Найди 10 входных значений, на которых два независимых разработчика по этой СТ реализуют разное поведение. Для каждого: значение, вариант А, вариант Б, какое требование неоднозначно, исправленная формулировка.»
2. «Ты — злонамеренный тестировщик. Найди способы получить пароль из системы: логи, URL, кеш браузера, ответы API, история формы. Какое требование это закрывает и где дыра?»
3. «Посчитай вручную балл, уровень и рекомендации для паролей эталонного набора по алгоритму раздела 5. Где твой результат не совпал с Приложением А — укажи шаг алгоритма.»
4. «Найди граничные значения для каждого правила и проверь, что эталонный набор их покрывает. Чего не хватает?»
5. «Пройди матрицу трассируемости в обе стороны: есть ли БТ без ФТ и ФТ без БТ?»
6. «Есть ли требования, которые нельзя проверить автотестом? Как их проверить вручную и что будет критерием?»
7. «Сравни все числа и тексты в БТ, СТ, API и UI. Выпиши расхождения.»
8. «Что сломается, если разработчик поменяет порядок шагов 3–6 алгоритма? Приведи пароль, на котором результат изменится.»

**Неудобные входы, которые стоит прогнать:** пароль из пробелов; эмодзи (длина в символах vs байтах); комбинирующие символы (é как e + ◌́); Unicode-цифры («٣»); «PaSsWoRd» (регистр в чёрном списке); « password» (пробел + слово из списка); одновременно повтор и последовательность («aaabc»); «890» и «zab» (переход через границу); 128 и 129 символов; JSON без поля password; password = 123 (число, не строка).
